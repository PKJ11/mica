    What this module covers

    Data engineering is the base on which analytics, BI and machine learning stand. In eight chapters we will see where data engineering fits, the stages every piece of data passes through, how data is ingested, stored and transformed, how data engineering is different from ETL, why data in motion (streaming) has become so important, how data is served and sent back into business tools through Reverse ETL, and the practices that keep all of this running every day.

    Most examples use Dhanvanshi Super Store, a supermarket chain with branches in Nagpur, Pune, Nashik and Aurangabad. Its suppliers and partners also appear: Kavya Distributors supplies the stores, Madavi Warehouse holds the stock and Niharika Logistics runs the trucks. FoodJoe, a food delivery app, and Aman Mart, a smaller grocery chain, come in wherever they make a point clearer.

    Chapter 1

    Where data engineering fits

    Data engineering is the work of building and running the systems that take raw data from where it is created and turn it into reliable, well-organised data that others can use for reports, analysis and machine learning.

    Upstream and downstream

    Think of a river. The water that reaches a city has come a long way from its source. If the water is dirty upstream, no filter in the city can fully clean it. Data works the same way. Data engineers work upstream: they bring data out of the source systems and make it clean and dependable. Data scientists and analysts work downstream: they take that data and turn it into forecasts, insights and decisions.

    Source systemsBilling counters, Dhanvanshi app, Kavya Distributors' invoices, truck GPS
    →
    Data engineeringUpstream. Collect, move, store, clean, model, serve
    →
    Data science and analyticsDownstream. Dashboards, forecasts, experiments, models
    →
    DecisionsWhat to order, which offer to send, which branch needs help

    Some people treat data engineering as a part of data science. Reis and Housley take a different view: the two are separate fields that support each other. Data engineers provide the inputs; data scientists and analysts convert those inputs into something useful. In small companies one person often does both. As a company grows, the two jobs separate, because each needs deep skills of its own.

    The data science hierarchy of needs

    Monica Rogati drew data work as a pyramid. Like Maslow's hierarchy of needs, each layer needs the layers below it. Many companies want to start at the top with AI. Rogati's point is that the top is only as good as the base, and the base is mostly data engineering. Tap a layer to see what it means at Dhanvanshi.

    Aman Mart's AI plan

    Aman Mart's owner has read about AI and wants a model that predicts which customers will stop coming. But Aman Mart's five stores use three different billing software, bills from two stores are shared on email as Excel files, and the customer's phone number is missing on a large share of bills. A data scientist hired today would spend most of the first months just finding and joining data. The first need is at the bottom of the pyramid.

    The data engineering lifecycle

    Tools in data engineering change every few years. The stages that data passes through do not. Reis and Housley call these stages the data engineering lifecycle, and they suggest learning the lifecycle first and the tools later.

    The lifecycle has five stages. Generation happens in the source systems. Then data is ingested, transformed and served, and it is stored at every one of these steps. Served data is used for analytics, for machine learning and, through Reverse ETL, it goes back into business tools. Below the lifecycle run six undercurrents: practices that apply to every stage.     Source systems and ingestion

    A data engineer rarely owns the systems where data is born, but has to understand them well. Ingestion is the step where data is taken out of those systems and brought into the data platform.

    Where Dhanvanshi's data comes from

    Why not run reports on the billing database itself?

    The billing database is an OLTP system (online transaction processing). It is built to save thousands of small bills quickly and correctly. A report such as "sales by product for the last two years" is an OLAP query (online analytical processing): it reads crores of rows at once. Running such queries on the billing database can slow down billing at the counter, and a queue at the counter on a Sunday evening is the last thing a store manager wants. So the data is copied into a separate system built for analysis.

    OLTP: billing database
    • Many small reads and writes
    • Current state: today's stock, this bill
    • Must respond in milliseconds
    OLAP: data warehouse
    • Few large reads, scanning many rows
    • History: every bill for years
    • A query can take seconds

    The ingestion choices

    Every ingestion pipeline answers four questions.

    • Batch or streaming? Batch collects data and moves it at intervals, for example every night at 2 AM. Streaming moves each record as soon as it is created. Chapter 6 covers streaming in detail.
    • Push or pull? In push, the source sends data out (Kavya Distributors emails its invoice). In pull, the data platform goes and fetches it (a job calls Niharika Logistics' API every 30 seconds).
    • Full or incremental? A full load copies the whole table every time. An incremental load copies only what has changed since the last run.
    • How do we find what changed? Either by a timestamp column such as updated_at, or by reading the database's own change log. The second method is called change data capture (CDC).

    When the source changes without telling you

    One morning the Kavya Distributors invoice load fails. Someone at Kavya renamed the column Qty to Quantity in their Excel template. This is called schema drift. Good data engineers talk to the owners of source systems, agree on what the data will look like (sometimes written down as a data contract), and build checks that catch such changes before the reports go wrong.

    Storage, modelling and transformation

    Once data is ingested, it has to be kept somewhere sensible, arranged in a shape that makes questions easy to answer, and cleaned so that the answers are right.

    Where analytical data is stored

    Data warehouseData lakeLakehouse
    What it holdsCleaned, structured tables for analysisAny data in any format: tables, JSON, images, logsLake storage with warehouse-style tables on top
    SchemaSchema on write: data must fit the table before it is loadedSchema on read: structure is applied when the data is readTables have a schema; files underneath are in open formats
    Good forReports, dashboards, SQL analysisCheap storage of everything, data science workBI and ML on one copy of the data
    ExamplesBigQuery, Snowflake, Amazon RedshiftAmazon S3, Azure Data Lake Storage, Google Cloud StorageDatabricks, tables in Apache Iceberg or Delta Lake format

    A lake without rules soon becomes a "data swamp": files nobody can find or trust. The lakehouse idea grew out of this problem. Many companies, Dhanvanshi included, keep data in three layers:

    RawExactly as it came from the source. Never edited. Sometimes called bronze.
    CleanCorrect types, no duplicates, standard names. Sometimes called silver.
    Business-readyJoined and summarised for a use: daily sales, customer segments. Sometimes called gold.

    Row storage and column storage

    A billing database stores data row by row, because it usually needs a whole bill at a time. Analytical systems mostly store data column by column (for example in the Parquet file format), because most analytical questions need only a few columns from a very large number of rows. Compare what each one reads for this question: total sales of Toor Dal 1 kg.

    Data modelling: the star schema

    Data modelling means deciding how tables are arranged. The most common design for analytics is the star schema, from Ralph Kimball's dimensional modelling. A fact table in the centre holds the measurements, one row per event. Dimension tables around it hold the descriptions used to filter and group those measurements.

    dim_productproduct, brand, category, pack size
    dim_branchbranch, city, region, manager
    fact_salesone row per item on each bill: quantity, amount, discount
    dim_datedate, week, month, festival flag
    dim_customerloyalty tier, city, joining date

    With this design, "sales of pulses in Pune branches during Diwali week" becomes one fact table joined with three small dimension tables. Bill Inmon's approach is the other classic one: first build one central, fully normalised warehouse for the whole company, then create smaller data marts from it. Most modern teams use a mix of both ideas.

    Transformation and data quality

    Transformation turns raw data into useful data. The common steps are fixing data types, removing duplicates, standardising names and codes, filling or flagging missing values, joining tables and applying business rules such as "net sales = gross sales − returns − discounts". Data quality is usually judged on six dimensions: accuracy, completeness, consistency, timeliness, uniqueness and validity.

    Chapter 5

    ETL, ELT and data engineering

    Many people still think data engineering means ETL. ETL is an important pattern, and a lot of data engineering grew out of it. But today it is one tool in a much larger kit.

    ETL: extract, transform, load

    ETL became common with data warehouses in the 1980s and 1990s. Storage and computing power inside a warehouse were costly, so data was first extracted from the sources, transformed on a separate ETL server, and only the finished, summarised result was loaded into the warehouse. Tools such as Informatica PowerCenter, IBM DataStage and Microsoft SSIS were built for this. The people who ran them were often called ETL developers.

    →
    Loadonly finished tables

    ELT: extract, load, transform

    Cloud warehouses such as BigQuery, Snowflake and Redshift changed the costs. Storage became cheap and computing power could be scaled up for a few minutes and then switched off. So teams started loading raw data first and transforming it later, inside the warehouse, mostly with SQL. Tools such as Fivetran or Airbyte handle the extract and load, and dbt is widely used for the SQL transformations.

    Extractfrom sources

    Loadraw data as it is
    →
    Warehouse
    →
    Transforminside the warehouse

    The biggest practical difference is that ELT keeps the raw data. When a new question comes up, the team writes a new transformation on data that is already there. With classic ETL, anything dropped during transformation is gone from the warehouse.

    So how is data engineering different from ETL?

    ETL and ELT describe how data moves from sources into a warehouse, in batches. That covers parts of two lifecycle stages: ingestion and transformation. Data engineering is the whole discipline. It also covers understanding source systems, streaming data, choosing and designing storage, data modelling, serving data to analysts and models, Reverse ETL, and the undercurrents: security, data management, DataOps, architecture, orchestration and software engineering practice. Job titles show this change: from ETL developer, to BI engineer, to data engineer around the early 2010s when big data tools like Hadoop arrived, and now to platform and analytics engineers as well.

    ETL has not disappeared

    Transforming before loading is still the right choice when data must be changed before it leaves a secure place, for example masking phone numbers or dropping Aadhaar numbers before data goes to the cloud. Many teams now do a small cleaning step before the load and the main transformation after it. This is sometimes written as EtLT.

    Chapter 6

    Data in motion

    Data at rest sits in a table until someone runs a query or a batch job. Data in motion is processed while it is flowing, one event at a time, seconds after it is created. More and more business decisions now depend on the second kind.

    Why data in motion matters more today

    Payments happen in real time. India's UPI handled a record 24.51 billion transactions in August 2026, worth ₹29.82 lakh crore, which is about 79 crore transactions a day on average. That is roughly 9,000 payments every second, round the clock. A fraud check on a UPI payment has to finish before the payment does. A report the next morning is of no use.

    Customers expect things instantly. Quick commerce delivers groceries in ten minutes, FoodJoe shows the rider moving on a map, and a customer expects the Dhanvanshi app to know that the last bag of atta was sold at the counter a minute ago.

    Many decisions are now made by software. Fraud blocking, surge pricing, stock reservation and delivery routing are automatic. Software can act on an event within milliseconds, so the data has to arrive that fast.

    Devices send data all the time. GPS units on Niharika Logistics trucks, temperature sensors in Madavi Warehouse and every smartphone running an app produce a continuous flow of events.

    The value of some data falls quickly. Knowing that a truck carrying frozen goods has a failing cooler is valuable in the first five minutes. Knowing it tomorrow only helps you write the insurance claim.

    The tools have become easier to use. Event streaming used to need a large specialist team. Managed services from cloud providers now make it possible for a mid-size company like Dhanvanshi.

    How fresh does the data need to be?

    Use caseAcceptable delayPattern
    UPI fraud check before a payment completesUnder one secondStreaming
    FoodJoe rider location and delivery timeA few secondsStreaming
    Stock shown on the Dhanvanshi appUnder a minuteStreaming
    Sales screen at head officeAbout 15 minutesMicro-batch
    Next week's order to Kavya DistributorsA dayDaily batch
    Monthly GST returnSeveral daysBatch

    Streaming is not always better. It costs more and is harder to build and fix. The right question is not "batch or streaming?" but "how fresh does this decision need the data to be?"

    The building blocks of streaming

    Producersapp, counters, trucks, sensors
    →
    Event brokerKafka, Kinesis, Pub/Sub
    →
    Stream processorFlink, Spark Structured Streaming
    →
    Sinkslive dashboard, app, alerts, lake
    • An event is a small record of something that happened, with the time it happened: "order O5521 placed at 12:58:03".
    • An event broker keeps events in order in a log and lets many consumers read them, each at its own pace. Apache Kafka is the best-known example.
    • A stream processor reads events as they come and filters, joins or counts them.
    • Change data capture turns every insert, update and delete in a database into an event, which links the batch world and the streaming world. Debezium is a popular open-source CDC tool.

    Two well-known designs combine batch and streaming. The Lambda architecture runs a batch pipeline and a streaming pipeline side by side and merges their results. The Kappa architecture uses only the streaming pipeline, and when history has to be recomputed it replays old events from the log.

    Counting a stream: windows and late events

    A stream never ends, so "total orders" has no final answer. Instead we count within windows of time. A tumbling window cuts time into fixed blocks that do not overlap, such as 12:00 to 12:05, 12:05 to 12:10. A sliding window has a fixed length but moves forward in smaller steps, so windows overlap: "orders in the last 10 minutes, updated every minute". A session window closes after a gap with no activity, which suits user sessions on an app.

    Events can also arrive late. A FoodJoe rider's phone may lose network, so an order placed at 12:58 reaches the server at 13:03. Event time is when it happened; processing time is when the system received it. Stream processors use a watermark, a rule for how long to wait for late events, before closing a window.

    Chapter 7

    Serving and Reverse ETL

    Serving is the last stage of the lifecycle and the one users actually see. If people do not trust or use the served data, the work in all the earlier stages is wasted.

    Serving data for analytics

    Most served data goes to business intelligence: dashboards and reports in tools such as Power BI, Tableau or Looker, and direct SQL queries by analysts. FoodJoe also does embedded analytics: each restaurant partner sees its own sales and ratings inside the FoodJoe partner app. For all of this, one thing matters more than speed: everyone must get the same answer. If the finance team's "net sales" and the store team's "net sales" differ, meetings turn into arguments about whose number is right. Many teams keep agreed metric definitions in one place, called a semantic layer.

    Serving data for machine learning

    Data scientists need training data and features: well-defined inputs such as "average weekly sales of this product at this branch over the last eight weeks". The same feature must be calculated the same way when the model is trained and when it makes live predictions. A feature store is a system that keeps features consistent for both uses.

    Reverse ETL: sending data back

    ETL and ELT move data from business systems into the warehouse. Reverse ETL moves data the other way: from the warehouse back into the tools people use every day, such as a CRM, a WhatsApp campaign tool, the billing counter screen or an advertising platform.

    Business systems
    Billing counters
    Dhanvanshi app
    Kavya Distributors' invoices

    Why is this needed? The warehouse is the only place where data from all sources comes together. It knows that a customer has spent ₹48,000 in two years but has not visited in two months. The billing counter does not know that, and neither does the WhatsApp tool. Staff will not open a dashboard before every customer interaction. Reverse ETL puts the insight where the work happens. This is also called data activation or operational analytics. Reis and Housley note that Reverse ETL was once seen as a bad practice, but it has become a normal part of the serving stage. Tools such as Hightouch and Census are built for it; teams can also write their own jobs that call each tool's API.

    • Dhanvanshi sends its "at risk" customers to the WhatsApp tool every morning for a win-back offer.
    • The cashier's screen shows "Gold member: offer ₹100 off above ₹1,500" when a loyalty number is entered.
    • Dhanvanshi pushes suggested reorder quantities into Kavya Distributors' order portal.
    • FoodJoe pushes a "kitchen delay score" back into each restaurant's partner app.

    Chapter 8

    The undercurrents

    Building a pipeline once is the easy part. Keeping it correct, secure and on time every single day, for years, is where most of a data engineer's effort goes. The six undercurrents are the practices that make this possible, across every stage of the lifecycle.

    UndercurrentWhat it meansAt Dhanvanshi
    SecurityGive people only the access they need, protect personal data, encrypt data and keep passwords and keys out of code.Analysts see phone numbers masked as 98XXXXXX21. Only the Reverse ETL job can read full numbers.
    Data managementGovernance, data ownership, a catalogue so people can find data, lineage showing where each number came from, quality rules, privacy and retention.The catalogue says who owns fact_sales, and lineage shows that the dashboard's "net sales" comes from the billing counters through three steps.
    DataOpsAutomated tests, monitoring and alerts, and a clear process when something breaks, so that problems are caught before users notice.If today's bill count from Nashik is 40% below normal, the data team gets an alert at 3 AM, not a call from the regional manager at 11 AM.
    Data architectureDesigning systems that meet today's needs and can change later, while keeping cost under control.Choosing a lakehouse so that dashboards and forecasting models use the same copy of the data.
    OrchestrationRunning many jobs in the right order, retrying failed ones, and showing what ran, what failed and why.The nightly pipeline in Apache Airflow; Dagster and Prefect are other popular tools.
    Software engineeringWriting pipeline code the way good software is written: version control, code review, testing, automated deployment, and infrastructure defined as code.Every SQL change is kept in Git, reviewed by a colleague and tested on sample data before it goes live.

    Orchestration: the pipeline as a DAG

    A nightly pipeline is not one job but many, and some must wait for others. This is drawn as a DAG (directed acyclic graph): each box is a task, each arrow means "this must finish first", and no path loops back on itself. When a task fails, the orchestrator stops only the tasks that depend on it. Everything else still runs.

    The data engineer as the owner of trust

    Users rarely praise a pipeline that works. They notice only when a number is wrong or late. Each undercurrent protects that trust from a different side: security protects customers, data management keeps meaning clear, DataOps catches failures early, architecture keeps the system able to change, orchestration keeps the order right, and software engineering keeps the code dependable.
